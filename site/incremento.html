Cómo se toman las seis figuras

Cada ficha incluye una muestra de cómo debe verse la captura, dibujada con los datos de este proyecto: el tablero de Trello, la tarjeta abierta, el modelo de datos y las pantallas del sistema. La muestra no es una imagen del sistema real, es la referencia para replicarla antes de capturar.

  • Tomar todas las capturas con el sistema en marcha y con los datos de demostración cargados; una pantalla vacía no demuestra que la funcionalidad opere.
  • Guardar en PNG, con un ancho mínimo de 1600 píxeles y un peso menor a 1,5 MB por archivo.
  • Usar siempre el mismo tema visual y el mismo tamaño de ventana en las figuras del sistema, para que las seis se lean como una sola entrega.
  • Ocultar correos de las cuentas, contraseñas, pestañas ajenas y barras de marcadores antes de capturar.
  • Respetar el texto del pie palabra por palabra: es el mismo que se inserta en el Word y el que figura en el plan de mejora.
  • Las figuras 5 y 6 deben mostrar el mismo conjunto de productos, para que el relato del incremento no se contradiga.

El enunciado de la T1 no fija un número de capturas: pide evidencias del sistema, formularios, base de datos, interfaces y tablero Scrum. El equipo fijó seis figuras para cubrir los cinco tipos de evidencia y sostener las cinco historias del Sprint 1. La figura del historial de commits quedó fuera por ser opcional en el enunciado.

HU-03: Registro de entradas y salidas de mercadería (Kardex)

Descripción

Como encargado de almacén, quiero registrar movimientos de entrada (compras/devoluciones) y salida (despachos/consumo) asociados a un producto, para actualizar el stock disponible automáticamente y conservar un historial trazable.

Criterios de aceptación 3/3

  • ✓ Dado que se registra una entrada de X unidades, cuando se confirma la operación, entonces el stock actual del producto se incrementa exactamente en X unidades y se guarda la fecha, hora y usuario responsable.
  • ✓ Dado que se registra una Salida mayor al stock disponible actual, cuando se intenta confirmar, entonces el sistema bloquea la operación con el mensaje "Stock insuficiente".
  • ✓ Dado que se registra una Salida válida, cuando se confirma, entonces se descuenta del stock actual y queda registrado en el historial de movimientos.

Tareas técnicas 5/5

  • ✓ Crear la tabla movimientos_inventario con tipo, cantidad, fecha, hora y usuario.
  • ✓ Alinear los nombres de los campos del formulario con las columnas de movimientos_inventario.
  • ✓ Actualizar el saldo de la tabla productos en cada entrada o salida.
  • ✓ Implementar la validación de stock insuficiente en salidas.
  • ✓ Verificar la validación de stock insuficiente en salidas.

PK = clave primaria · FK = clave foránea · UNIQUE = valor único

Tres tablas alineadas de izquierda a derecha en el orden en que se usan: primero usuarios, luego productos y al final movimientos_inventario, que apunta a las otras dos. Así se lee de un vistazo que el movimiento es el que une al usuario con el producto.

Qué demuestra El incremento tiene persistencia relacional real: la trazabilidad de quién hizo cada movimiento se sostiene en el modelo y no en el relato.

La captura debe mostrar

  • Tabla usuarios: id, usuario, clave_hash, rol, activo.
  • Tabla productos: id, sku, nombre, categoria, unidad_medida, stock_actual, stock_minimo.
  • Tabla movimientos_inventario: id, id_producto, tipo, cantidad, fecha_hora, id_usuario.
  • Claves primarias y foráneas marcadas, con la relación usuarios 1 a N movimientos y productos 1 a N movimientos.

Evitar

  • Mostrar la contraseña en texto plano: el campo se llama clave_hash y así debe verse.
  • Nombrar la clave foránea producto_id en un sitio e id_producto en otro: ese desajuste fue el impedimento registrado en la figura 2.
  • Capturas de un cliente de base de datos con tema oscuro: no se imprimen bien en el Word.
